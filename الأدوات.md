# الأدوات — FLIXO Tool & Capability Operating Book

> **المرجع الوصفي والتنفيذي الموحد لمنظومة أدوات FLIXO.**

هذا الملف ليس قائمة أسماء، وليس backlog مزخرفًا، وليس وعدًا بأن كل ما ورد فيه قابل للتشغيل. إنه **سجل معرفة وتشغيل وتطور** يربط كل Tool/Capability بمصدرها، وحدودها، وعقدها، وحالتها، وأدلة تحققها، وطريق انتقالها من الفكرة إلى القدرة التشغيلية.

**المبدأ الحاكم:** الاسم يثبت أن القدرة فُكّر فيها؛ العقد يثبت كيف يجب أن تعمل؛ التنفيذ يثبت أنها موجودة؛ الـVerifier يثبت أن الناتج صحيح؛ وExact SHA يثبت أي حقيقة تم اعتمادها.

**قاعدة عدم التضخيم:** لا يجوز استخدام عدد الأدوات التاريخي، أو عدد تعريفات Registry، أو عدد الكلمات/الـintents، كبديل عن عدد القدرات التنفيذية المثبتة.

**قاعدة عدم فقدان التاريخ:** لا نحذف الأصول التخطيطية القديمة عند ظهور حقيقة أحدث؛ نربطها بالحالة الحالية، ونوضح ما تم استبداله وما بقي صالحًا.

> **حالة هذه النسخة:** هذا الـOperating Book يعيش على فرع `agent-tools-consolidation-20261006`. مرجع الحقيقة البرمجية هو أحدث HEAD حيّ على الفرع، وليس رقم Commit ثابتًا داخل وصف قد يصبح قديمًا بعد التعديل.

## 1. لماذا هذا الملف مهم؟

الهدف ليس جمع الوثائق في ملف طويل؛ الهدف هو تحويل المعرفة المبعثرة إلى **نظام قابل للفهم واتخاذ القرار والتنفيذ والتدقيق**.

يجب أن يستطيع مهندس أو Agent أو Reviewer الإجابة من هذا الملف، دون تخمين أو تضخيم، عن الأسئلة التالية:

1. ما هذه القدرة؟ وما المشكلة التي تحلها للمستخدم؟
2. هل هي تاريخ، Candidate، أم جزء من النطاق التنفيذي الحالي؟
3. ما العقد الذي يحكم مدخلاتها ومخرجاتها؟
4. أين تنفذ: محليًا، في Worker، أو عبر خدمة مستضافة؟
5. ما الـEngine أو المكتبة أو الـProvider الذي تعتمد عليه؟
6. كيف نثبت أن الناتج صحيح وليس مجرد نجاح شكلي للتنفيذ؟
7. ما حدود الأمان والخصوصية والأداء؟
8. ما الذي يمنع تفعيلها أو ترقيتها الآن؟
9. ما الدليل المرتبط بالـExact SHA الذي يسمح باعتبارها حقيقة حالية؟

لذلك فإن **كل Tool هنا يجب التعامل معها كCapability Contract**، لا كاسم في جدول.

## 2. قاموس الحقيقة — لا تخلط بين هذه الأشياء

| المصطلح | المعنى الدقيق |
|---|---|
| Tool | وحدة تنفيذ محددة يمكن استدعاؤها بعقد واضح |
| Capability | قدرة وظيفية قد تُنفذ عبر Tool واحد أو Engine مشترك أو سلسلة خطوات |
| Engine | طبقة تنفيذ مشتركة تحمل عائلة من القدرات |
| Intent | هدف المستخدم بصيغته الطبيعية؛ ليس Tool بحد ذاته |
| Alias | صياغة بديلة لـIntent؛ لا تنشئ قدرة جديدة |
| Registry Entry | تعريف canonical للقدرة؛ لا يكفي وحده لإثبات التنفيذ |
| Contract | القواعد النوعية والحدود التي تحكم التنفيذ والمدخلات والمخرجات |
| Verifier | مكوّن مستقل يتحقق من الناتج الفعلي مقابل العقد |
| Evidence | دليل قابل للمراجعة يثبت ادعاءً محددًا |
| Exact SHA | هوية الحالة البرمجية التي أنتجت الدليل |
| Planning Status | مرحلة القدرة في التخطيط والتنفيذ |
| Runtime Status | الحالة التشغيلية للوحدة في Runtime |
| Capability State | مدى اعتراف النظام بالقدرة وقابليتها للتخطيط والتنفيذ |

**قاعدة ذهبية:** `READY` ليست مرادفًا لـ`MVP`، و`REGISTERED` ليست مرادفًا لـ`VERIFIED`، و`VERIFIED` ليست مرادفًا لـ`ACTIVE` ما لم تستوفَ جميع بوابات الإصدار المطلوبة.

### 5.2 بطاقات الوصف القياسية لكل Tool / Capability

كل Tool جديدة أو موجودة يجب أن تحصل، عند نضوجها، على بطاقة وصف قابلة للتحويل مباشرة إلى عقد واختبارات:

```text
[IDENTITY]   ID / Name / Family / Engine
[WHAT]       ماذا تفعل؟
[WHY]        ما قيمة المستخدم؟
[INPUT]      المدخلات والصيغ والمعلمات
[OUTPUT]     الناتج وشكله وشروطه
[MODE]       أين وكيف تنفذ؟
[DEPEND]     ما الذي تعتمد عليه؟
[VERIFY]     كيف نثبت صحة الناتج؟
[LIMITS]     ما الحدود المعروفة؟
[SAFETY]     ما المخاطر وضوابطها؟
[PRIVACY]    ما مسار البيانات؟
[PERF]       ما الميزانية والحدود؟
[RECOVERY]   ماذا يحدث عند الفشل؟
[LOCALIZE]   ما المطلوب للغات/السياقات؟
[EVIDENCE]   ما دليل الـExact SHA؟
```

## 6. قاعدة اختيار الـTool من الـIntent

```text
User Intent
  ↓
Normalize language / aliases
  ↓
Match canonical capability
  ↓
Validate capability state
  ↓
Validate parameter schema
  ↓
Build ToolPlan
  ↓
Execute
  ↓
Verify actual artifact
```

الـIntent أو alias أو الكلمة العربية لا تُنشئ Tool جديدة، ولا تُنشئ Registry جديدة، ولا تمنح صلاحية تنفيذ.

## 7. معايير الجودة الوصفية

وصف Tool ممتاز يجب أن يكون:

**دقيقًا:** يصف السلوك لا الانطباع.

**قابلًا للاختبار:** يمكن تحويله إلى acceptance criteria.

**مقيدًا:** يذكر ما لا تدعيه القدرة.

**قابلًا للربط:** يحدد الـID والـEngine والعقد والدليل.

**غير تسويقي:** لا يستخدم «يدعم كل شيء» أو «نتيجة مثالية» دون دليل.

**ثنائي الغرض:** يفهمه الإنسان ويمكن للـAgent تحويله إلى قرار تخطيط دون اختراع خصائص.

## 8. بروتوكول تشغيل هذا الملف

عند بدء أي مهمة Tools، يجب على Agent تنفيذ الترتيب:

```text
READ → CLASSIFY → CHECK SCOPE → CHECK DUPLICATE → CHECK CONTRACT
→ EXECUTE → VERIFY → RECORD EVIDENCE → UPDATE STATUS
```

وعند وجود تعارض:

```text
RUNTIME CANONICAL TRUTH
        >
CURRENT VERIFIED EVIDENCE
        >
CURRENT PLAN
        >
HISTORICAL PLAN
```

مع الاحتفاظ بالتاريخ وعدم حذفه.

## 9. تعريف «Done» للأداة

لا تُغلق Tool كـActive لمجرد:

- وجود UI؛
- وجود route؛
- وجود function؛
- وجود Registry entry؛
- مرور build فقط.

الإغلاق يتطلب، بحسب applicability:

```text
Contract
+ Implementation
+ Registry Parity
+ Targeted Tests
+ Output Verification
+ Security / Privacy Evidence
+ Performance / Browser Evidence
+ Exact SHA
+ Required CI / Governance Gates
= CURRENTLY PROVEN CAPABILITY
```

## 10. قاعدة عدم الحذف وعدم التضخيم

هذه الوثيقة **append-only في المعرفة التاريخية**، لكنها **truth-aware في الحالة الحالية**. يجوز إضافة correction/status/cross-reference، ولا يجوز حذف المصدر التاريخي لإخفاء التناقض.

لا يجوز عدّ:

```text
aliases + intents + registry rows + roadmap entries + historical plans
```

كأنها:

```text
independently verified executable tools
```

## 11. كيف يستخدمه الإنسان والAgent والـRed Team؟

**الإنسان:** يحدد الأولوية والسياسة ونطاق الإصدار.  
**Agent:** يقرأ الملف قبل المهمة، ويظل مقيدًا بالـCanonical Runtime Authority.  
**Reviewer:** يراجع العقد والأدلة والتناقضات والحالات غير المكتملة.  
**Red Team:** يبحث عن طرق تجعل الاسم أو الـRegistry أو الـroute تتنكر في هيئة قدرة تنفيذية.  
**Release/Certification:** يعتمد على evidence مرتبطة بالـExact SHA، لا على الوصف وحده.

## 12. مؤشر الجاهزية المقارن

للتقييم المقارن فقط، وليس لترقية الحالة تلقائيًا:

```text
Readiness =
Scope
+ Contract
+ Implementation
+ Registry
+ Verification
+ Security
+ Privacy
+ Performance
+ Localization
+ Evidence
```

كل محور يحمل: `PASS / FAIL / PENDING / N/A`.  
النتيجة الرقمية ليست Runtime status؛ أي بوابة إلزامية FAIL تمنع التفعيل.

## 13. سجل التغيير الوثائقي

عند كل تحديث مهم لهذا الملف، يجب أن يظهر في PR/commit:

- ما الذي تغير في **الوصف**؟
- ما الذي تغير في **الحالة**؟
- ما الذي تغير في **العقد**؟
- ما الذي تغير في **الدليل**؟
- ما الذي بقي **تاريخيًا فقط**؟
- وهل تغير نطاق الـMVP؟ إن لم يتغير، يجب التصريح بذلك.

## 14. سجل المصادر المدمجة

كل مصدر تاريخي محفوظ هنا يُعامل كـ**نسخة معرفية** لا كسلطة تنفيذية تلقائية. السلطة التشغيلية تبقى في تعريفات Runtime وExecution Gate وVerifier المعتمدة.

## 15. دورة حياة موحدة قابلة للتنفيذ

```text
DISCOVERED
→ NORMALIZED
→ DEDUPED
→ CANDIDATE
→ ADMITTED
→ IMPLEMENTING
→ REGISTERED
→ TARGETED TEST PASS
→ OUTPUT / ARTIFACT VERIFY PASS
→ SECURITY / PRIVACY PASS
→ PERFORMANCE PASS
→ LOCALIZATION PASS
→ EXACT-SHA EVIDENCE
→ ACTIVE
```

Planning Status منفصل عن Runtime Lifecycle وCapability State:
- Planning: `CANDIDATE | ADMITTED | IMPLEMENTING | VERIFIED | BLOCKED`
- Runtime: `experimental | beta | ready | deprecated`
- Capability: `RECOGNIZED | PLANNABLE | EXECUTABLE | UNAVAILABLE`

The authoritative input remains the tool registry. A tool is registered once; shared indexes and contract consumers derive the rest.

## Core model

```text
Tool Definition
   ↓
TOOL_REGISTRY
   ↓
TOOL_CATALOG
   ├── byId
   ├── byPath
   ├── byAlias
   └── ready
   ↓
Router / SEO / Sitemap / i18n / Browser Matrix / Certification
```

## Scaling invariants

1. Tool identity is unique and stable.
2. Canonical paths are unique.
3. Aliases cannot collide with canonical paths or other aliases.
4. Readiness is explicit; non-ready tools are never promoted by inference.
5. Components remain lazy-loaded so registering more tools does not eagerly execute all tool modules.
6. Runtime consumers perform indexed lookup rather than repeatedly scanning the full registry.
7. Operational metadata is additive and typed; missing classification is surfaced instead of silently guessed.

## Complexity target

Registry validation is `O(n)` at initialization. Normal lookup is `O(1)` through maps. Adding a tool therefore does not require adding another per-tool router table or per-tool lookup loop.

## Management contract

Each future tool should eventually declare an operational profile covering lifecycle, execution model, capabilities, contract levels, output class, security profile, localization scope, browser ownership, and evidence requirements. This metadata belongs beside the tool identity and should be consumed by generic engines.

The current foundation intentionally does not invent execution metadata for existing tools. The migration path is:

```text
unclassified → explicitly classified → contract-enforced → certified
```

## Test ownership

`test-tool-platform-catalog` verifies the shared catalog boundary once. Per-tool behavior remains owned by the canonical tool contract/browser test, preventing the catalog layer from becoming a second copy of application tests.

## Performance direction

At 1,000 tools, the platform should avoid:

- importing every tool implementation during discovery;
- scanning all tools for every route request;
- maintaining duplicated registry copies for router/SEO/sitemap;
- generating a bespoke test suite for each administrative concern.

The intended architecture is one registry, one indexed catalog, shared contract engines, and data-driven matrices.
