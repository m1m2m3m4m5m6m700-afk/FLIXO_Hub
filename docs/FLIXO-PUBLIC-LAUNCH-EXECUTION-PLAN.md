# FLIXO Hub Public Launch Execution Plan

Status: ACTIVE / BLOCKED_WITH_EVIDENCE
Last updated: 2026-10-19
Baseline candidate observed: `29f2e0fe045689337a1483ed98d087b736ff6afc`

This document defines the release sequence and acceptance evidence. It is a plan, not a release certificate. Every gate must be re-evaluated against the exact candidate SHA after any code or configuration change.

## Release invariants

- Production truth is `main`; implementation and integration should use the `execution` lane and reviewed pull requests.
- Do not push directly to `main`, force-push, bypass required checks, or treat an agent's report as certification.
- Raw user File/Blob bytes must never be sent to an LLM, provider, or backend in the MVP local editing path.
- Provider and database credentials remain server-side. Never expose secrets through `VITE_*` variables.
- Do not modify `src/worker.ts` during Phase 0 remediation unless a separately scoped and reviewed task explicitly requires it.
- A build alone does not certify a public launch. CI, security, Red Team, production identity, and browser evidence must all bind to the same exact release SHA.
- Historical evidence is context only and must not be reused as current candidate evidence.

## Phase 0 — Freeze and qualify a release candidate

### 0.1 Resolve the candidate

1. Read the current `main` head and record the full 40-character SHA.
2. Compare it with the intended candidate; if the branch has advanced, restart candidate qualification from the new head.
3. Use a disposable remediation branch and pull request for fixes. Never mutate `main` directly.
4. Do not create `v1.0.0-rc.1` until all mandatory checks pass on the same final SHA.

### 0.2 Security remediation

1. Inspect the complete Gitleaks job logs and record only finding metadata (rule, path, line, commit and fingerprint); do not copy secret values into reports.
2. Distinguish live credentials from test fixtures, synthetic samples, signed/expiring URLs, historical snapshots, and documentation examples.
3. Treat any potentially live credential as compromised: rotate/revoke it with the owning provider and remove it from active source/configuration. Do not add broad allowlists to make the scanner green.
4. Add a narrowly scoped, documented allowlist only after confirming a finding is a non-secret false positive. Scope it to the exact rule and file/commit where supported.
5. Re-run the full-history secret scan on the candidate SHA and retain the new run URL and result.
6. Ensure client-exposed `VITE_*` values contain public configuration only, never credentials.

### 0.3 Governance channel

1. Run the Agent Blocked Channel verifier and inspect its logs.
2. Confirm the required repository labels `agent-blocked` and `agent-blocked-global` exist with exact names.
3. If a label is missing, create it through the authorized GitHub repository settings/API; do not weaken or skip the verifier.
4. Re-run the workflow and retain the result.

### 0.4 Reproducible build evidence

Use Node.js 22 as declared by `.nvmrc` and `package.json`.

```bash
node -v
npm -v
npm ci
npm run build
```

If any command fails, stop release qualification, retain the full log, diagnose the cause, and retry only after a specific correction. Never report a build as successful without an actual run.

After a successful build, verify and record:

- `dist/` exists and contains built assets.
- `dist/robots.txt` and `dist/sitemap.xml` exist.
- Physical SPA route entries generated by the route-generation build step exist.
- The build contains the expected immutable FLIXO identity artifact for the candidate SHA; its content must match the candidate SHA exactly.
- The identity verifier and static Worker behavior remain fail-closed.
- A deterministic SHA-256 digest of the build output is recorded. Hash a defined file list or deterministic archive; do not claim a directory hash without defining the algorithm.

### 0.5 Phase 0 acceptance

Phase 0 may be marked CLOSED only when all items below are evidenced on the same final SHA:

- [ ] Candidate SHA recorded and stable.
- [ ] `npm ci` succeeds under Node.js 22.
- [ ] `npm run build` succeeds.
- [ ] Required static files, route entries, assets, and SHA identity artifact verified.
- [ ] Full-history Secret Scan passes, with every suppression justified and narrowly scoped.
- [ ] Agent Blocked Channel passes with the required labels present.
- [ ] Required trust-gate checks are green.
- [ ] Manifest records real build time, candidate SHA, output digest, file inventory, and evidence URLs.
- [ ] Tag `v1.0.0-rc.1` is created only after all required checks are green on the same SHA.

## Phase 1 — Pre-deployment qualification (checklist only until Phase 0 closes)

- [ ] Verify required CI and trust-gate status for the final candidate SHA.
- [ ] Verify CodeQL and dependency/security audit results for that SHA.
- [ ] Verify Red Team/security boundary tests for that SHA.
- [ ] Verify browser E2E and desktop/mobile smoke evidence for that SHA.
- [ ] Verify production deployment identity returns the exact expected SHA.
- [ ] Verify production smoke tests and rollback target.
- [ ] Confirm public copy matches the canonical capability registry and does not overstate capabilities.
- [ ] Confirm privacy boundaries, including local File/Blob handling, remain intact.
- [ ] Confirm no unresolved critical/high security findings.
- [ ] Record evidence links and explicit PASS/FAIL for every gate before any promotion.

## Deployment and launch-day sequence

Follow `docs/FLIXO-LAUNCH-DAY-RUNBOOK.md` for T-24h, T-1h, T0, post-launch monitoring, and incident response. Publish only after required evidence is green and bound to the same release SHA. Production fixes invalidate candidate-specific evidence and require fresh qualification.

## Evidence recording format

For each check record: check name, PASS/FAIL/BLOCKED, repository, branch, exact 40-character SHA, workflow/run URL, run timestamp, and relevant artifact/hash. Redact credentials and do not store secret values in logs or documentation.

A release certificate is valid only when all mandatory checks, production identity, and browser evidence agree on the same exact release SHA.
