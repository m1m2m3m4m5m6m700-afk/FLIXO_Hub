# FLIXO — المهام.md
## Canonical Agent Task Ledger

هذا الملف هو **مرجع التكليف التشغيلي الوحيد للوكلاء** داخل مستودع FLIXO.

القاعدة الأساسية:
- المهمة القابلة للتنفيذ لا تُعتبر موجودة إلا إذا كانت في قسم **ACTIVE DISPATCH QUEUE** أدناه.
- الملفات الأخرى قد تكون **Policy / Evidence / Historical / Candidate Source**؛ لا يجوز لها أن تولّد dispatch مباشرة.
- أي مهمة مكتملة بالكامل تُحذف من الـACTIVE QUEUE بعد تنفيذ بروتوكول **VERIFY → REMOVE → COMMIT → RECOUNT**.
- المهام المؤجلة أو التاريخية محفوظة في سجل الحمل المرحّل، لكنها **ليست dispatchable** حتى تتم إعادة اعتمادها صراحة.
- أي SHA داخل وثيقة دليل هو سياق تاريخي فقط. عند التنفيذ يجب حلّ live ref وexact candidate SHA من GitHub.

## 1. AUTHORITY MODEL

### Production
`main` = production truth.

### Integration
`execution` = canonical implementation/integration lane.

### Promotion
`execution → pull request → required checks → independent review → main`.

### Agent authority
الوكلاء يحق لهم التفتيش، التخطيط، التنفيذ، الاختبار، الإصلاح، التوثيق، والمراجعة على `execution` ضمن المهمة المسندة. لا يحق لهم:
- الكتابة المباشرة إلى `main`؛
- إعلان release certification؛
- إنشاء Registry/Executor/Verifier/Authority ثانية؛
- إضعاف required checks أو إخفاء failure؛
- تحويل Evidence تاريخي إلى Fresh Evidence.

المرجع العام لعقد الوكيل: `AGENTS.md`.

## 2. SOURCE CLASSIFICATION

عند اكتشاف ملف أو خطة جديدة يجب تصنيفه أولًا:

| CLASS | المعنى | هل ينشئ مهمة تلقائيًا؟ |
|---|---|---|
| TASK | تكليف تنفيذي صريح | نعم، بعد إضافته لهذا الملف |
| POLICY | قيد أو عقد حاكم | لا؛ يقيّد المهام |
| EVIDENCE | إثبات أو تقرير تحقق | لا؛ يدعم مهمة قائمة |
| CANDIDATE | PR/فرع/تغيير مقترح | لا؛ يحتاج integration task |
| HISTORICAL | سجل قديم أو بنية متقاعدة | لا |
| DEFERRED | مطلب غير داخل النطاق الحالي | لا، حتى إعادة الاعتماد |

قاعدة الاكتشاف:
**أي مصدر جديد يحتوي قرارًا تنفيذيًا أو gap حقيقيًا يجب تحويله إلى Task Card هنا؛ أما المصادر التي تثبت التنفيذ فتربط بالمهمة ولا تصبح مصدر dispatch ثانٍ.**

## 3. TASK CARD CONTRACT

كل مهمة نشطة يجب أن تُعرّف بهذه الحقول، وبنفس الترتيب:

`TASK_ID`
`TYPE`: IMPLEMENT | VERIFY | INTEGRATE | GOVERNANCE | RELEASE | AUDIT
`PRIORITY`: P0 | P1 | P2 | P3
`OWNER`: Agent role / human owner
`STATUS`: QUEUED | IN_PROGRESS | BLOCKED | OWNER_ACTION | VERIFYING
`SCOPE`: الملفات/المسارات المسموح بها
`DEPENDS_ON`: Task IDs
`SOURCE`: المصدر الأصلي للمطلب
`EVIDENCE`: روابط/ملفات الإثبات
`ACCEPTANCE`: شروط الإغلاق الدقيقة
`NEXT_ACTION`: خطوة واحدة قابلة للتنفيذ
`COLLISION_KEY`: سطح التعارض

لا تُعتبر المهمة منتهية بسبب ACK فقط، أو نجاح اختبار واحد، أو source inspection، أو تقرير وكيل آخر، أو historical SHA، أو PR description.

## 4. AGENT LIFECYCLE

**DISCOVER → CLAIM → BASELINE → EXECUTE/VERIFY → ACCEPTANCE → REMOVE → COMMIT → RECOUNT**

### CLAIM
غيّر Status إلى `IN_PROGRESS` مع Owner وCollision Key. لا تُنفّذ مهمة يملكها وكيل آخر على نفس Collision Key.

### BASELINE
حلّ live `execution` SHA، وافحص `main` وPRs والفروع ذات الصلة.

### EXECUTE/VERIFY
افحص implementation الحالي أولًا. لا تعيد إصلاحًا مثبتًا على نفس SHA.

### ACCEPTANCE
يجب أن تتطابق implementation + tests + evidence + documentation + candidate lineage.

### REMOVE
بعد اكتمال القبول فقط: أعد التحقق من current SHA، احذف بطاقة المهمة كاملة فقط، ولا تحذف الدليل المرجعي، ولا تعدّل بطاقة وكيل آخر.

### COMMIT
Commit واضح يتضمن Task ID.

### RECOUNT
أعد عدّ بطاقات `### EXEC-` تحت ACTIVE DISPATCH QUEUE. **ACTIVE TASK COUNT = 0** يعني عدم وجود تكليف تنفيذي مفتوح.

## 5. SHARED LEDGER SAFETY

ملف المهام مورد مشترك ويجب التعامل معه كـcritical coordination surface.
- لا blind overwrite.
- لا تحديث متزامن للـLedger من وكيلين.
- قبل أي كتابة: fetch أحدث نسخة من `execution`.
- إذا تغيّر SHA منذ القراءة: أعد fetch وادمج التغيير بدل الاستبدال.
- Agent mutation على source يمكن أن تكون متوازية؛ **Ledger mutation نفسها متسلسلة**.
- Worker branch ليس production authority.
- أي SHA drift يبطل Evidence السابق المرتبط بالـcandidate.

## 7. STATUS SEMANTICS

`QUEUED` = جاهزة للتكليف بعد baseline.
`IN_PROGRESS` = owner claimed the task.
`VERIFYING` = implementation exists and fresh qualification/evidence is being produced.
`BLOCKED` = blocker known and unresolved.
`OWNER_ACTION` = requires authority outside the current agent execution surface.
`VERIFIED` / `CERTIFIED` are terminal evidence states; after recording the evidence, remove the card from ACTIVE QUEUE.

## 11. ARCHITECTURE NON-GOALS / EXPLICIT REJECTIONS

المسارات التالية ليست مهامًا تنفيذية حالية إلا إذا أعيد اعتمادها صراحة:
- historical public Agent API/provider gateway;
- historical Agent Editor runtime;
- second execution registry/executor/verifier;
- cloud/server media execution for the browser-local MVP;
- historical 20-tool / 100-tool / 200-tool scope inflation;
- legacy repair swarm/watchdog/council runtime authority;
- arbitrary autonomous capability self-promotion;
- fake support for formats/backends not actually implemented;
- certification based only on repository documentation.

## 12. AGENT STARTUP PROCEDURE

عند استلام أي Task ID:
1. اقرأ `AGENTS.md` وهذا الملف.
2. ابحث عن Task ID داخل ACTIVE QUEUE وتحقق من Owner/Collision Key.
3. حلّ live `execution` SHA و`main` SHA.
4. افحص current source/tests/CI/PR/history قبل mutation.
5. صنّف FACT / GAP / BLOCKER / INSUFFICIENT_EVIDENCE.
6. نفّذ أقل mutation لازمة فقط.
7. شغّل targeted tests ثم regression المناسبة.
8. حدّث Evidence بالـexact resulting SHA.
9. عند اكتمال Acceptance احذف البطاقة، لا تضع `DONE` وتتركها.
10. COMMIT ثم RECOUNT.
11. إذا كان هناك SHA drift، أعد qualification ولا تستخدم evidence القديم.

## 13. ZERO-QUEUE DEFINITION

**ACTIVE TASK COUNT = عدد بطاقات المهام `### EXEC-*` تحت ACTIVE DISPATCH QUEUE غير المحذوفة.**

عندما يصبح العدد صفرًا:
- لا توجد مهمة تنفيذية مفتوحة في الـLedger؛
- لا يعني ذلك تلقائيًا أن المنتج Certified؛
- certification/release governance يظل منفصلًا ويحتاج أدلته الخاصة.
